# K70 boot04：已进入 XNU/BSD，根设备挂载失败

用户要求暂停 USB 检测后，继续从已知 trace02 启动路径排查。随后已将
本页 boot04 镜像刷入 boot_b，发送、写入和重启均返回 OKAY。
原厂 vendor_boot_b 保持此前恢复后的内容，未写 userdata。

用户随后提供的两张本轮照片显示 XNU BootProgressMin 已运行，日志到达
`159 bsd_init: calling setconf?`，最终显示
`failed to mount root device @IOKitBSDInit.cpp:984`。这证明本机已执行
XNU 并进入 BSD 初始化；尚未挂载根卷、启动 launchd 或进入系统桌面。
当前内核的原生 UFS/root publication 仍关闭，boot04 不包含 OS 根卷。

照片可读寄存器为 TCR `0x22a51a251a`、SCTLR `0x3454593d`，
pages `0x3e31`、free `0x3736`。后者约 55.2 MiB；当前 UFS 实现需要
约 69.9 MiB 存放 OS/SystemOS 的完整认证哈希表，还不计用户态。

boot04 只使用原厂 DXE Heap `0xBAB00000..0xC7CC0000`，将四个未经本机
确认的 gap/high bank 保留，移除动态添加内存的驱动。专用 DarwinBoot
使用显式 128 MiB 窗口，保持 256 MiB 默认值，不回落其他物理地址。
读取负载前核对真实 HOB/FDT/initrd，发现与堆冲突或未保留输入即拒绝。
这不能证明更早的 UEFI 内存分配已安全，也不提供完整系统内存预算。

实际 trace02 Mach-O 字节复核确认：入口 `0xfffffff00741e488` 的
`1400001e` 正确跳到 `0xfffffff00741e500`，固定蓝条探针的 44 字节
均有可执行 segment 文件字节支持，随后跳到 `_start_first_cpu`
`0xfffffff00742005c`。没有发现文件/VM 偏移错误。本轮照片已证明真实内核执行。
