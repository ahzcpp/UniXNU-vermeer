# boot05r3：修正 alloc-ranges 的语义

r2 真机画面显示有效的 8 个 RAM bank、21 个 GCD NonExistent 区间，但合格片段数为 0。其中 `R31..R47` 包含 `0..FFFFFFFF`、`0..FFFFFFFFFFFFFFFF` 等整个候选地址范围；核对源码确认，解析器此前把动态保留节点的 `alloc-ranges` 追加到了已占用 Reserved 列表。这是语义错误：该属性表示未来分配可以选择的范围，实际静态占用由 `reg` 或 FDT reserve map 表示。[DeviceTree 正式 schema](https://github.com/devicetree-org/dt-schema/blob/main/dtschema/schemas/reserved-memory/reserved-memory.yaml)、[Linux reserved-memory 实现](https://github.com/torvalds/linux/blob/v6.6/drivers/of/of_reserved_mem.c) 均支持这个区别。

r3 将已审阅的 17 个尚未实例化的 Android/Linux 请求单独计为 `DEFER`：16 个具名 `shared-dma-pool`、带 `reusable` 且无 `no-map` 的 CMA 池，以及形状受限的 `debug_kinfo_region`。CMA 的 size、alignment 和 placement 按合法有界 cell 元数据检查，不把与物理占用无关的池尺寸固定成单一值；正式 DTBO54 的 qseecom 54→64 MiB、TA 16→200 MiB 变体均可接受。未知名称、未知所有权语义、改变兼容/保留标志或畸形参数仍拒绝。**只要出现 reg，始终优先作为静态保留区排除。**

debug_kinfo 单独要求 size=4096、no-map、没有 reusable/compatible/alignment，并核对 phandle 真正链接到 `/soc/google,debug-kinfo`、其 compatible 为 `google,debug-kinfo`。Google 固定版本驱动在 probe 中先查 Linux `reserved_mem` 分配结果，要求有效 base/size 后才写当前 Linux 内核信息。这里的结论是：本次 direct-XNU 路径未运行 Linux reserved-memory 分配器，该精确 size-only 请求尚未实例化；固件可能读取由 Linux 生成的 kinfo，不能据此宣称固件永远不用它。[Google 驱动固定源码](https://android.googlesource.com/kernel/common/+/1694e2760e48d82ce4cc30a196d93fef6ae1f69d/drivers/android/debug_kinfo.c)

四个占位描述符及其 HOB 完全不动；没有 FreePages、GCD 重分类或物理内存探测。发布范围仍必须属于真实 FDT bank 与当前 GCD NonExistent 的交集，并排除所有实际 reg/reserve-map 区间和活跃 FDT/initrd。r3 同时纳入先完整验证再排序的 QualifiedUnion 修正，避免无序坏输入被排序移入已验证槽位而漏检。

定向验证通过：

- 实际生产解析器在原厂 base DT 与 DTBO54-composed DT 上均得到 DEFER17、unknown0；静态保留项分别为 30/35，原始 DT 的 RAM reg 为零，因此这些宿主输入不能证明手机可用 RAM。
- 合成 bank 上的动态请求、reg 优先、未知池、改变标志、畸形约束、debug consumer 链接/形状拒绝，以及 1500 轮逐页集合对照通过 ASan/UBSan。
- 实际生产发布器的提交/部分失败/禁止重试模型通过；QualifiedUnion 的 3000 轮集合对照及乱序未对齐、倒置、空区间等回归用例通过。
- 模块编译/链接、serial GenFds、全部模块/SEC 内存表绑定审计、完整 Android/FAT/FD/DTB 解包回读通过。
- 准备脚本在隔离临时工作区从冻结 r2 源码重建当前运行时/脚本，逐字节比较零差异。

高地址证据需要区分内核身份：`high-pa-entry-readonly.json` 的机器字检查绑定完整系统 storage 内核 `962381af…`，其 TCR 对应 PA40 bit，physBase 是全宽 x 寄存器加载。r3 使用另一份基线内核 `4559b648…`，这里只引用加载器/入口源码的 64 bit 路径及 boot04 已显示的真实 TCR；不把 storage 二进制报告冒充 r3 基线实证。真机 FDT 的 B05/B06 地址低于 2^36，r3 高地址 XNU 启动尚未实测，UFS DMA/SMMU 地址宽度也未获验证。
