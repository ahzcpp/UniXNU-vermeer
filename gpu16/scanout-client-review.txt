Scanout client revision 3

Both options are disabled by default. k70-scanout-verify=1 compares a bounded
number of complete scaled frames using aligned volatile 32-bit reads. It is
diagnostic only; do not use that mode to measure frame rate. The original
unscaled first-four-frame comparison is removed.

k70-scanout-pace=60 waits after the GPU finishes and COMPLETE_SWAP succeeds,
before requesting the next frame. Interrupted and early sleeps retry against
the monotonic deadline. Errors, bounded retry exhaustion and early releases
are counted. This limits client admission; it does not establish physical
panel refresh or prove that the compositor produces 60 frames per second.

The PF progress report changes independently: first frame, first failure,
then every 120 frames instead of every 5. This reduces per-character kernel
calls in ordinary operation.

Local validation before this commit:
- All five workflow patches apply together on isolated pinned driver copies.
- Actual scaled AIR: 32 cases / 17,511,720 pixels, independent host comparison.
- Revised pacing wrapper: 261 checks, clang++18 with ASan/UBSan, including a
  sleep interrupted after 999 ns; the same wrapper retries to the deadline.
- The unchanged pixel verifier previously passed 868 cases / 423,100,213
  pixels with independent reference and planted-error checks in Claude's
  local handoff. Those are host results, not hardware results.

Real macOS SDK compilation and device testing are still required. On the
previous binary, the Settings main page showed horizontal black stripes
even though PF reported successful copies. Pixel correctness takes priority
over cadence benchmarking; successful submission is insufficient evidence.
No firmware, signing keys, phone identifiers or connection credentials are
included in this branch. Do not merge the branch automatically.

Display-source publication follow-up (test169 / test170)

patch-source-publication.py reproduces the exact isolated display164 -> 169
source transformation. It requires the qualified input SHA and refuses output
overwrite. The reproduced output matches the compiled test169 source SHA.
It maps the existing held IOSurface descriptor read-only Copyback, performs
the same source flush used by the working CPU fallback, releases that map,
then offers the frame to the existing GPU presenter. Mapping failure falls
back to the unchanged CPU path. No pixels are read or written by this block;
early-retire remains zero. This is not a global driver coherence-policy fix.

Device evidence: test169 full Settings scanout CRC matched and was visually
normal; the prior test167 source16-pixel black stripes disappeared. The
scripted continuous Settings-scroll transfer rate was 58.6414 FPS (active
interval median 59.7846), with no app memory-pressure kills, recover or panic.
Test170 with the genuinely built revision3 addon, both options off, showed
normal Settings and 58.7108 FPS (active median 59.7667), likewise without those
failures. These short tests do not prove every application, owner-death
cleanup, physical panel refresh, or all future producer/cache aliases safe.
Mapping effects and timing have not yet been isolated from cache maintenance.
The optional pace60 comparison is still pending; do not enable it merely
because its argument contains 60. CI run43340673362 built userspace at ffbbdcf;
this display-only follow-up does not change that userspace build input.
